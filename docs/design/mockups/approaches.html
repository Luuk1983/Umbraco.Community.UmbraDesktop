1 · In-process windows

Each window is a normal DOM subtree that mounts an Umbraco element inside a draggable frame. Context API isolates them automatically (the modal precedent). Seamless: shared state, trivial cross-window drag/drop.

Single tools: works today Trees/internal nav: needs a small virtual-router capability (~4 engine files) Pure package? mostly — nav-heavy windows want a core PR

2 · Iframe windows

Each window is an <iframe> running the real backoffice at a deep-link URL. Every iframe owns its own location/history/router — so full independent navigation comes for free, with zero engine changes.

Internal nav everywhere: free Pure package? 100% — no core changes Heavy: each window re-boots the shell Cross-window sharing/drag: postMessage only

3 · Hybrid  recommended

In-process windows for single-element tools — your permissions editor + access viewer ship basically now, zero engine changes — and reach for an iframe only for the rare "full section with its tree" window. Best of both, and defers the hard call.

Your real use case: immediate Pure package for the 90% you care about Upgrade path to the full dream stays open

My recommendation: Hybrid. Start fully in-process (your two tools basically work today), and only later decide whether "content-library-in-a-window" is worth an iframe or a small virtual-router contribution to core. You never block yourself, and the first demo is close.
